# 書き出しパッケージ（review package）の仕様

対象読者: バーの「zip」ボタンで生成されるzipを受け取り、修正を行う側（人間・AIどちらでもよい）。

**この文書は `rv-layer.js` の実装（2026-08-19、コミット `9208bc25` 時点）を読んで書いている。
確認できた挙動だけを書き、確認できていない箇所は `[未確定]` と明記する。推測では埋めていない。**

## いつ作られるか

バー右側の「zip」ボタンを押すと、未済み（`status !== "done"`）のコメントだけを
対象にzipを1つ生成し、ブラウザのダウンロードとして保存する。済みコメントは含まれない
（対応済みなので再送の必要がない、という設計）。

未済みコメントが0件のときは何も作らずトースト「未済みコメントはありません」を出す。

## ファイル名

```
rv-<docslug>-<YYYYMMDD>-<HHMM>.zip
```

`docslug` はページのファイル名（拡張子を除く）を `[A-Za-z0-9_-]` 以外を `-` に置換し、
先頭末尾の `-` を落として40文字に切ったもの。例: `example.html` → `example`。

zipファイル自体の名前は`docslug`（ページファイル名由来）しか含まないため、`index.html`のような
一般的なファイル名を持つ複数ページを同じタイミングで書き出すと、ダウンロードフォルダ上で
zipのファイル名が同じ・または似た名前になりうる（ブラウザ側の重複回避で末尾に番号が付く形に
なる）。ただし**zipを展開すれば `source/<元のファイル名>` に実体HTMLが入っている**ため、
中身を見ればどのページのzipかは判別できる（下記「zipの中身」参照）。zipファイル名だけで
一意に判別したい場合の追加案（文書タイトルやディレクトリ構造を織り込む等）は未実装。

## zipの中身

```
rv-<docslug>-<YYYYMMDD>-<HHMM>.zip
├── review.md
├── source/<元のファイル名>.html
└── images/
    ├── <name>.<ext>
    └── ...
```

`source/` には対象HTMLそのものが1ファイル入る。対応する側はzipを展開するだけで
「何を直すか」が揃った状態になる（レビュー依頼者が別途元ファイルを渡す必要はない）。

### `source/` の元ファイル名

`sourceFileName()` が決める。ページのURLパス末尾（`LEGACY_DOC`）が `.html`/`.htm` で
終わっていればそれをそのまま使い、そうでなければ `docSlug() + ".html"` にフォールバックする
（例: 拡張子なしのパスで配信されているページ等）。

### `source/` の中身の取得経路（2通り）

`getSourceHtml()` が決める。**fetchが使える場合は常にfetchを優先する**（改変ゼロで最も正確）。

1. **`fetch`（主経路）**: `location.protocol` が `http:`/`https:` のとき、`fetch(location.href,
   {cache:"no-store"})` でページを再取得し、レスポンステキストをそのまま使う。取得したHTMLは
   ブラウザが今表示しているDOM状態とは無関係の「サーバー/ファイルシステム上の実体」そのもの
2. **DOMシリアライズ（フォールバック）**: `location.protocol` が `file:` 等でfetchが効かない、
   またはfetchが失敗した（HTTPエラー・ネットワークエラー）場合に使う。`document.documentElement`
   を丸ごとクローンし、注釈UIの要素（`#rvbar` `#rvpop` `#rvtoast` `#rvdonepanel` `#rvorphan`
   `#rvmarks` `#rvsel` `#rvhover` `#rvcrop` `#rvguide`）と本文へ差し込んだ `mark.rv`
   （＋その中の `.rvnum`）を
   取り除いてから `outerHTML` を書き出す。`<script src="....rv-layer.js">` の読み込み行と、
   既存の `window.__rvResolved` の埋め込みは注釈UIではないため**取り除かず残す**（消すと次の
   レビューの往復ができなくなるため）。`body` に付いていた `rvpicking` クラスも外す
   （枠選択モード中に書き出した場合の後始末）

どちらの経路で取得したかは `review.md` の「元HTMLの取得経路」欄に明記される
（下記「`review.md`の生成規則」参照）。DOMシリアライズ経路は「属性順序等に軽微な整形差が
出ることがある」という注記付きで案内される。

## `review.md` の生成規則

`reviewText(imageResult, open, sourceInfo)` 関数が組み立てる。**この関数はzip専用で、
バーの「コピー」ボタンが使う `copyText()` とは別関数**。1人で使う（チャットへ貼るだけの）
コピー文字列は `copyText()` が組み立てる（末尾に指示、画像は**ファイル名のみ**を書き、
探し方を添える。ブラウザは保存先の絶対パスを確実には取得できないため、存在が保証
できないパスは書かない）。**zip同梱の `review.md` はそれとは別フォーマットで、
「対応する側が読み落とさないこと」を優先して構成が組み直されている**（下記参照）。

### 構成（上から順）

```markdown
# HTMLレビュー修正指示

- 編集対象: source/<元のファイル名>
- 文書タイトル: <document.title>
- 書き出し日時: <YYYY-MM-DD HH:MM>
- 未済みコメント: <N>件
- 元HTMLの取得経路: fetch（サーバー/ファイルから再取得。改変なし） / DOMシリアライズ（...）

## AIへの対応手順

対応が済んだら、source/<元のファイル名> の改訂版の </body> 直前に

<script>window.__rvResolved={rev:"r{YYYYMMDDHHMMSS}",ids:["対応したid",...]}</script>

を埋め込むこと（revは毎回ユニークに。注釈レイヤーが次回表示時に自動で済みへ落とす）。

**番号（下の「1.」「2.」…）は表示用の見出しで、正本は各コメントの id。
ids配列には番号でなくidを入れること。**

[〔枠〕コメントがあれば注記]
[〔切り取り〕コメントがあれば注記]
[画像添付コメントがあれば注記]

## コメント

### 1. <コメントID>

- 種別: テキスト / 枠 / 切り取り
- セクション: <見出し>
- 対象: 「<引用テキスト>」
- 修正指示: <コメント本文>
- 追記:
  - <追記1>
  - <追記2>
- 添付:
  - images/<zip内ファイル名>
  - images/<zip内ファイル名>（サムネイルのみ・原寸なし）
  - <元のファイル名>（zip未収録：原寸を取得できず、サムネイルもなし）

### 2. <コメントID>
...
```

**旧版（README等の下書き段階）との違い**: 以前は「コメント本文が先、対応手順とidの正本
宣言は末尾」という構成だったが、**長い指示の末尾は読み落とされるという判断から、対応手順と
「idが正本」の宣言を冒頭（コメント本文より前）へ移した**。zipを渡す相手がAIでも人間でも、
最初に読む部分に手順を置く設計。

### 各項目の詳細

- **編集対象**: `source/<元のファイル名>`。ファイル名の決め方は上の「`source/`の元ファイル名」節
- **未済みコメント件数**: `openComments()`（`status !== "done"`）の件数
- **種別**: 3種類。`kind:"block"` → 「枠」、`kind:"crop"` → 「切り取り」、それ以外（無印＝
  テキスト選択）→ 「テキスト」
- **対象**: 引用テキスト（`c.quote`）の改行をスペースへ正規化したもの
- **修正指示**: コメント本文（`c.note`）の改行をスペースへ正規化したもの
- **追記**: `c.replies` がある場合のみ出力。読み手が既存コメントを開いて足した指示で、
  本文とは別に時系列で積まれる。**本文だけを読むと追記された指示が落ちる**
- **添付**: 画像がある場合のみ出力。各画像の表記は下表の3パターン

| 状態 | 表記 |
|---|---|
| 原寸（IndexedDB由来）またはサムネイル代用が取得できた | `images/<zip内ファイル名>` |
| サムネイルしか無く原寸が取れなかった | `images/<zip内ファイル名>（サムネイルのみ・原寸なし）` |
| 原寸もサムネイルも無い | `<元のファイル名>（zip未収録：原寸を取得できず、サムネイルもなし）`（`images/`パスは付けない＝存在しないパスを書かない） |

以下は該当するコメントが1件でもあるときだけ、「## AIへの対応手順」節の中に追加される注記:

- `〔枠〕`種別のコメントがある → タグ名・クラス・引用テキストで特定すべき旨
- `〔切り取り〕`種別のコメントがある → px寸法・囲み要素・引用テキストが手がかりである旨
- 画像添付があるコメントがある → 各コメントの「添付」に `images/` パスがあるものだけ
  同梱されている旨（「zip未収録」はコメント本文だけで対応する旨）

済み消し込みの契約そのもの（`rev`/`ids`の意味、二重適用防止、IDが正本という規約）は
[resolved-contract.md](resolved-contract.md) を参照。この文書は「zipの中でその契約がどう案内されるか」だけを扱う。

## 画像ファイルの実体

### 元のファイル名（コメントが保持する名前）

添付時に `flushImages()` が発行する。形式:

```
rv-<docslug>-<コメントID>-<連番>.<拡張子>
```

連番は、同じコメントIDに紐づく既存の名前（保存済み・ポップアップ内どちらも）を避けて
最小の空き番号を割り当てる。編集で途中の画像を外して新規追加しても、削除された番号を
再利用せず次の空き番号を使う（旧ファイルとの衝突を避けるため）。

### zip内のファイル名

`images/` 配下に置く際、拡張子は**元の名前の拡張子ではなく、実際にzipへ入れるBlobの
MIMEタイプから決め直す**。原寸（IndexedDB）が使えるときは原寸のMIME、原寸が無くサムネイル
（JPEG）で代用するときはJPEGの拡張子になる。これは「PNG原寸が失われてJPEGサムネイルで
代用したのに拡張子だけ`.png`のまま」という不整合を避けるため。

同名衝突が起きた場合は `-2`, `-3`... を付けて一意化する（`uniqueExportName`）。

### 対応MIME→拡張子

`imageExt()` が対応する既知の型: JPEG, PNG, GIF, WebP, AVIF, SVG, BMP, ICO, TIFF, HEIC,
HEIF, APNG。未知の`image/*`はMIMEのサブタイプ、それも取れなければ元ファイル名の拡張子を使う。

### 原寸とサムネイルの関係

- **原寸**: 添付時にIndexedDB（データベース名 `rv-layer`、オブジェクトストア `images`）へ
  Blobとして保存される。書き出し時はここから取り出す
- **サムネイル**: 添付時に長辺320pxへ縮小してJPEG品質0.6でエンコードしたdata URI。
  コメントのJSON本体（`localStorage`）にはこちらだけが残る（原寸は保存しない設計）
- IndexedDBが使えない環境（プライベートブラウジング等）では原寸が保存されず、書き出し時は
  常にサムネイル代用になる
- コメント削除・画像削除時はIndexedDB側の該当エントリも削除される（`deleteImages`）

## 文字コード・zip形式

- `review.md` はUTF-8（サロゲートペア対応の手書きエンコーダ `utf8Bytes()` を使用）
- zipはmethod=0（無圧縮=stored）の最小実装を自前で組み立てる。外部ライブラリ・CDN依存なし
- zip内のファイル名もUTF-8。ローカルファイルヘッダ・セントラルディレクトリの両方で
  UTF-8フラグ（`0x0800`）を立てている（日本語ファイル名でも文字化けしない）
- ZIP64には非対応。ファイル数65,535件超、または合計サイズが4GB近くになる場合はエラーを投げる
  （通常のレビュー用途では到達しない想定）

## 書き出しトーストの補足表示

書き出し完了時、フォールバック件数・欠落件数が0でなければトーストに件数を添える。
例: 「書き出しました（サムネイル代用 1件 / 画像欠落 1件）」
